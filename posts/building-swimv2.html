Building SWIMv2: Automating Network Upgrades at Enterprise Scale

The story is not “I wrote a Python tool for upgrading devices.” The story is that I helped build an enterprise automation platform capable of coordinating software upgrades across more than 1,000 network devices during a maintenance window.

That distinction is the whole job. A tool runs a command. A platform owns the operational process: who is in the window, whether the box is healthy, whether the image is actually on the device, whether the HA peer is ready, whether the change ticket is open, and what the logs say when something fails at 2 a.m.

The expensive problem

Network software upgrades are still one of the most labor-heavy operations in a large enterprise. They consume maintenance windows, contractor hours, and the attention of people who should be designing the next change instead of babysitting the current one. The work is familiar: copy an image, stage it, validate disk and licenses, upgrade, confirm version, handle failover, update the ticket, do it again on the next device.

At small scale, a good engineer with a terminal can survive that. At enterprise scale, it becomes a coordination problem. You cannot staff your way through 1,000 devices in a night. You need software that makes the workflow repeatable.

Why SWIMv1 was not enough

There was already an older SWIM. It was useful in a Client WAN / Cisco-shaped world, and it leaned on Ansible, YAML, Jinja, and scripting patterns that a lot of network automation careers start with. I came up through that world. It teaches you the devices. It does not give you a product.

SWIMv1 was not designed for broad multi-vendor scale. Adding another platform meant stretching a model that assumed too much about Cisco workflows. The interesting work in v2 was not “write more playbooks.” It was treating image management as an application: a web UI, backend services, background orchestration, parallel execution, validation, history, and change management as a first-class part of the run.

What we actually built

SWIMv2 is Software Image Management as a full-stack system. Operators work in a web application. The application does not do the long work inside an HTTP request. A backend orchestration layer owns reachability, pre-validation, image operations, upgrades, post-validation, execution state, logging, and results.

The workflow is phased on purpose:

  • Pre-validation — is this device even a candidate?
  • HA preparation — if there is a peer, is it ready?
  • Image copy — get the bits where they need to be.
  • Pre-maintenance — capture state and backups before you touch production.
  • Stage — prepare the image on the target.
  • Upgrade — execute the change.
  • Post-maintenance — prove the version, health, and sync you claimed you would deliver.
  • History — leave a record someone can read tomorrow.

ServiceNow is in that loop. The platform can open the change, associate the execution, update the ticket as the run proceeds, and close it when the workflow completes. Automating CLI without automating the change lifecycle still leaves a pile of human glue.

Start with one vendor, then generalize

F5 was the first implementation because it was a manageable place to establish the architecture. The F5 work is API-driven — image upload and copy, staging, upgrade, HA/active-standby handling, license and disk checks, image integrity, backups, version verification — and it became the pattern for treating vendor specifics as modules instead of a new script each time.

From there the platform expanded across Cisco IOS, IOS-XE, NX-OS, Versa, Citrix/NetScaler, Palo Alto, and Arista. Citrix, for example, is not “the F5 code with the names changed.” Guest targeting on SDX, authentication versus connectivity failures, and image-copy versus full upgrade are different problems. The reusable piece is the workflow and the orchestration, not the vendor SDK.

What I actually did

I did not receive a finished spec and type until the ticket closed. I helped lead SWIM as technical/product work: roadmap, PBIs, breaking large capabilities into executable pieces, coordinating contractor development, working with SMEs, establishing implementation patterns, and contributing to the code. That combination matters. Building software and steering the product are different skills, and this platform needed both.

The result is a reusable enterprise platform rather than a collection of one-off scripts. It has run upgrades involving 1,000+ devices in a single night. It reduced millions of dollars in contractor and operational effort — not because a script is clever, but because the operational process itself became software.
