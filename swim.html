Building SWIMv2

Enterprise network upgrade automation — a full-stack platform, not a script.

1,000+ devices Coordinated in a single maintenance window
Multi-vendor One platform, many network technologies
Millions saved Reduced contractor and operational effort

What it is

Software Image Management, rebuilt as a product

SWIM is Software Image Management. SWIMv2 is an enterprise platform for automating the end-to-end process of upgrading network infrastructure. It is a full-stack web application — not a playbook collection — with a user interface, backend services, background orchestration, image management, validation, logging, history, and enterprise change-management integration.

I helped design the platform, set technical direction, break the work into executable pieces, coordinate contractor development, and contribute directly to the code. The goal was a reusable automation product, not a pile of vendor-specific scripts.

The problem

Large-scale network upgrades traditionally require substantial manual engineering effort, coordination, maintenance-window management, and contractor involvement. Work is device-by-device, vendor-by-vendor, and tightly coupled to whoever happens to be on the change that night.

That does not scale. It is expensive, hard to repeat, and difficult to observe when something goes wrong at 2 a.m. across hundreds of devices.

The idea

Create a centralized automation platform that can perform the operational workflow end-to-end: pre-validation, image movement, staging, upgrade, post-validation, and change-ticket lifecycle — in parallel, across vendors, with a record of what happened.

SWIMv1 had been oriented around Client WAN / Cisco workflows and Ansible-heavy patterns. It was useful, but it was not designed for broad multi-vendor scale. SWIMv2 started over as software architecture: APIs, background jobs, reusable workflow phases, and vendor-specific behavior encapsulated behind common interfaces.

The platform

A web application backed by distributed/background orchestration for large-scale parallel network operations.

Web app → Backend → Orchestration → Device automation → Network devices

ServiceNow sits beside the workflow, not after it. The platform can open a change, associate an execution, update the ticket as work proceeds, and close it when the run completes. That is the difference between automating device commands and automating the operational process around a network change.

The workflow

A typical upgrade is a sequence of phases. Common structure is reused; vendor-specific behavior lives inside each phase.

Pre-validation Confirm the device is healthy and meets requirements before maintenance.
HA preparation For high-availability pairs, prepare and validate the standby before touching production.
Image copy Transfer the required software image and supporting files to the infrastructure.
Pre-maintenance Capture state, backups, statistics, and other pre-change information.
Stage Prepare the image and configuration on the target device.
Upgrade Execute the software upgrade itself.
Post-maintenance Verify version, health, sync, connectivity, and required conditions.
History Record what happened and expose logs and results in the application.

Multi-vendor by design

F5 was the first implementation because it was a manageable place to establish architecture and patterns — including API-driven operations rather than SSH-only scripting. Those patterns then expanded to additional vendors. The point is a scalable platform, not a one-off tool tied to a single network OS.

From SWIMv1 to SWIMv2

SWIMv1

Focused on Client WAN / Cisco environments. Relied heavily on Ansible, YAML/Jinja, and scripting patterns. Useful in a narrower domain, but not built for broad multi-vendor reuse.

SWIMv2

A software-oriented platform: multi-vendor support, API-driven automation, background orchestration, parallel execution, validation, observability, and ServiceNow integration. Built to scale.

Engineering challenges

The interesting problems were not “run this command on a box.” They were reliability and coordination at scale.

Parallel execution Many devices in one window, without treating the network as a serial checklist.
Reachability & errors Separate connection failures from authentication failures and generic operational errors.
Vendor differences Reuse the workflow; encapsulate image copy, HA, and upgrade behavior per platform.
HA / failover Active-standby pairs need preparation, sync, and ordered upgrades — not a blunt reboot.
Validation Disk space, licenses, image integrity, version checks, and post-change health.
Change management Tickets are part of the run: open, update, close — not a separate spreadsheet after the fact.
Long-running work Upgrades do not fit in a web request. Orchestration has to own state, logs, and history.
Observability Operators need execution output and a record of what happened on every device.

Outcome

A reusable enterprise platform rather than a collection of one-off scripts. The same system can copy images, stage upgrades, validate devices, run in parallel, and close the change — across vendors, at a scale of 1,000+ devices in a night.

That is the career story: moving from network scripting to building automation products that solve expensive operational problems.
